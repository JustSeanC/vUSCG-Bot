The 5.7 guard table has a stored constant `allowed = 1` and a unique key. Generated child expressions return 1 for valid rows and 0 for the same invalid conditions rejected by 8.4 CHECKs. InnoDB rejects 0 because no matching key can exist. Generated expressions and foreign keys have no cascade or trigger requirement. The constraints cover the same null checks as the original DDL. The app still enforces verified identity, accepted report ownership, track scope, role confirmation and input validation. Privileged bypasses through DDL, `foreign_key_checks=0` and unreviewed direct writers remain outside the application trust boundary. Keep strict mode and FK enforcement on, verify the installed definitions with read-only metadata, and keep runtime grants scoped.

Both fixtures exercise JSON, `DATETIME(6)`, UTC timestamps, enum literals, composite and nullable unique indexes, insert/upsert semantics and standard InnoDB locking. Training foreign keys stay within vUSCG tables using matching types/collations. 007 adds no FK against phpVMS model IDs. Identifiers stay within MySQL's 64-character identifier limit. The fixture key widths fit the server's default InnoDB configuration. Confirm the actual instance's row format and index limits, especially for the existing 191-character polymorphic key. DDL on 5.7 commits implicitly and a multi-statement import can leave earlier statements applied. Measure metadata lock and disk/rebuild costs on a representative staging clone. Inspect actual definitions after interruption before retrying. Existing data, nonce retention and native ownership markers are part of rollback planning.

## Release holds and hosting options

| Severity | Hold and required evidence |
| --- | --- |
| Critical | Native PIREP acceptance concurrency remains unresolved. Discord, manual/native admin, API and background writers need a proven common transaction and lock protocol or a verified enforceable writer restriction. Keep production bridge decisions disabled. |
| High | Native awards and type/trainee ratings require installed model, mapping and real writer evidence. The award pair permits competing external writes. Do not enable missing or uncoordinated mappings. |
| High | IP permissions/cache and Discord graduation require native authorization and real staging evidence, including cache retry and rank/role convergence. Keep those targets off. |
| High | The actual phpMyAdmin grants, backup/restore, exact staged table definitions, SQL mode/primary connections and the 007 maintenance window are unverified. Require measured rehearsal and signed evidence before a production cutover. |

**Option A — Continue on 5.7.44.** Use the version-specific path on authorized staging first. It enforces the reviewed integrity constraints and preserves existing data. MySQL 5.7 has reached upstream end of life, so confirm the provider's security maintenance and backup commitments. Require all native application and production gates independently of the database result.

**Option B — Move to a provider-supported MySQL release.** Ask the provider to validate a supported upgrade or logical migration path, phpVMS and Laratrust compatibility, SQL mode/collation differences, downtime, backups and restoration. The logical fixture rehearsal covers P07 SQL only. Provider-supported MySQL upgrade paths require intermediate versions or an independently verified logical migration approach. Preserve P07 guards on a restored 5.7 schema. Do not reapply the root training files on top of it. New 8.4 installs use the existing 8.4 definitions. Pursue provider migration if the operator cannot sustain 5.7 security support or the verified constraint/strict-mode configuration.

Recommended next release gate is a controlled rehearsal on a sanitized copy of the actual MySQL 5.7.44 and phpVMS build using the phpMyAdmin procedure. Keep all P05/P06 holds through this work.
