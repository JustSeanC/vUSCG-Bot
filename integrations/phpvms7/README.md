# P01 native phpVMS PIREP review

The Discord bot sends a signed decision to the existing VuscgCustom module. The module permits pending reports to move to accepted or rejected through `PirepService::changeState()`. Pending polling, trainee threads and message reconciliation continue using database reads. Discord buttons fail closed when the bridge is unavailable. The production bot and phpVMS installation can be upgraded separately.

## Cutover gate

The [P03 staging guide](../../docs/training-p03.md) includes the native-accounting fixture test and cross-writer acceptance checks.

Keep `PIREP_BRIDGE_DECISIONS_ENABLED` disabled until you have verified exclusive processing of the reports assigned to the bridge. The supplied native admin controller reads a PIREP without a locking transaction. Native acceptance updates pilot totals before saving the report state. A native or third-party writer may therefore read stale pending state and award duplicate credit even when the bridge locks its database rows. The gate is an operator assertion and does not remove access to other writers. In staging, use an isolated database and keep all other PIREP writers away from the fixtures. For production, use enforced exclusive routing/writer isolation or first make all state-transition entry points use the same locking and fresh-state protocol. A staff convention alone does not prevent a race.

The bridge uses a single transaction on the PIREP connection and locks the report, pilot and aircraft for competing bridge requests. Confirm InnoDB and a shared primary connection for all native writes. It does not retry the transaction. Audit the deployed `app/Providers/EventServiceProvider.php`, registered listeners for `PirepAccepted`, `PirepRejected`, `ProcessAward` and `UserStatsChanged`, plus `App\Services\UserService` and listeners registered by installed modules. These were not included in the reference. Native events fire inside the transaction. External actions or immediate queue dispatch may escape rollback or observe uncommitted data. Verify listener behavior, queue after-commit settings, and the exact phpVMS build before enabling production decisions.

## Installation

1. On a staging clone, confirm the PHP version, deployed phpVMS build, and VuscgCustom's enabled state in the module manager. Compare the live module route file before editing it. Preserve any site-specific routes.
2. Copy `modules/VuscgCustom/Http/Controllers/Api/PirepReviewController.php` to its matching path. Merge the new route group from `modules/VuscgCustom/Http/Routes/api.php` into the site's existing file. Copy `config/vuscg_pirep_review.php` to the Laravel application config directory. No phpVMS core edits are included.
3. Apply `bridge-nonces.sql` to the PIREP database. Configure a recurring purge of expired nonces using `DELETE FROM vuscg_pirep_review_nonces WHERE expires_at < UNIX_TIMESTAMP() - 300`. Retain that grace period and synchronize clocks across app, database and bot hosts. The table stores used nonces after authentication, including failed decisions. Its primary key rejects concurrent reuse across web workers.
4. Generate 32 random bytes as lowercase hex with `openssl rand -hex 32`. Store the same output as `PIREP_BRIDGE_SECRET` in secure runtime settings for Laravel and the bot. Keep `PIREP_BRIDGE_DECISIONS_ENABLED` false in Laravel initially. Set the bot's `PIREP_BRIDGE_URL` to the HTTPS application base URL, before `/api`. Restrict access to Laravel's config cache because it contains the secret. Rotate both sides together.
5. Configure HTTPS and Laravel's trusted-proxy handling for the actual ingress. Enforce an ingress body limit of 1 KiB on the two paths, and rate limits suitable for the bot's egress IP. The module also checks body size and uses Laravel's 30 requests per minute throttle. Use a shared limiter store if serving through multiple instances. Avoid logging signature headers, secret values, and raw request bodies. Restrict this endpoint to the bot's egress at ingress where practical.
6. Clear stale Laravel caches with `php artisan config:clear` and `php artisan route:clear`. Use `php artisan route:list --path=api/vuscgcustom/pirep-review` to verify that both POST routes load. Rebuild config and route caches if used by this installation, then reload long-running workers. Check the route listing again. Cache configuration is read at runtime and the existing example routes keep their existing access rules.
7. Test signed status with decisions disabled. A correctly signed request for a nonexistent ID returns 404 with `not_found`. Invalid signatures, timestamps over 60 seconds from server time, and reused nonces within the window return 401. Status uses POST for the signed JSON body and never changes a PIREP. The signature message joins the HTTP method, full path, Unix timestamp, lowercase 32-character hex nonce, and exact JSON bytes with LF, without a trailing delimiter. Use HMAC-SHA256 with the literal hex secret string as the key. The authenticated reviewer fields are included in the signed decision body. Laravel logs the Discord ID and optional linked C-number on confirmed bridge changes.

## Controlled validation and rollout

Run `npm run check` and `npm test` in the bot checkout. To run the included PHP feature tests, copy `tests/PirepReviewBridgeTest.php` into the staging application's `tests/Feature` directory. Use a disposable MySQL database with the nonce table and a pending PIREP linked to a pilot and aircraft. Set `PIREP_BRIDGE_TEST_PENDING_ID` for the fixture test and run `php artisan test --filter=PirepReviewBridgeTest` with the application's testing configuration. This exercises the HTTP handler and verifies native service delegation using a mock.

Before a live cutover, test the actual service on disposable fixtures with decisions enabled. Snapshot the pilot's hours, flight count, rank and location, and the aircraft's hours, fuel and location. Approve a pending fixture, verify the persisted state and expected native accounting and events, then submit duplicate and competing decisions with fresh nonces. Run competing requests concurrently against a fresh fixture and confirm only one changes it. Verify that the losing response and status response reflect the persisted state. Reject a separate pending fixture and verify its state, accounting and rejection events. Check listener effects after both commit and a controlled failure. Verify timeout reconciliation and that Discord keeps controls when phpVMS still reports pending. Confirm existing pending-thread and View behavior. Use no production reports.

Install and verify the PHP side first. After the cutover gate is satisfied, configure and restart the staged bot, then verify Discord role enforcement and resolution through its buttons. Keep the existing bot in production until validation is complete. A gateway or API problem may leave a request running after the bot's timeout. The bot checks status once with a new signature and does not resend the decision. Have the reviewer verify the current state before acting again.

## Rollback

Disable decisions and refresh Laravel config before removing routes or reverting the bot. Allow in-flight transactions to finish and check affected reports in phpVMS. Use native admin review only after those requests finish. If restoring the previous bot release, its review buttons will resume direct SQL writes. Keep those buttons out of service if native admin review is required. Restore the previous module route file or remove only the added group, remove the bridge controller and config as appropriate, and refresh caches. Revoke the shared secret. Keep the nonce table through the signature validity window and any investigation. Reverting code does not reverse committed flight accounting or events.
